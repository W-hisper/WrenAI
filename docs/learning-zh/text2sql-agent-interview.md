# 智能问数项目面试梳理：从 Workflow 到细粒度 Agent

> 整理依据：项目截图与后续补充说明。
> 目标岗位：Agent 开发。
> 文中的项目演进来自你的描述；提示词模板、工具契约、评测方案等未确认细节，会标为“建议准备”或“设计示例”，不能直接当作已完成工作。

## 1. 项目主线：逐步解决上下文、计算可信度和反馈粒度

一句话介绍：

> 我做的是一个自然语言问数与分析系统，围绕业务上下文构建、SQL 查询可靠性和数据分析可信度，经历了固定 Workflow、大工具封装、Skill 配合 Python 分析，以及细粒度 Agent 工具调用几个阶段。

整个系统服务于下面的业务过程：

```text
用户提出业务问题
  → 定位数据表与业务口径
  → 生成并执行 SQL
  → 获得查询结果
  → 计算分析指标、生成图表
  → 输出分析结论
```

介绍时最重要的主线不是“用了哪些技术”，而是：

```text
什么信息不足或行为不可控？
  → 如何观察到问题？
  → 做了什么改造？
  → 解决到什么程度？
  → 还剩下什么限制？
```

个人职责请单独补充：

> 我主要负责【实际负责的模块】，包括【具体设计与实现】，其他模块由【团队协作情况】完成。

## 2. 四个阶段的架构演进

| 阶段 | 主要实现 | 改造动机 | 获得的能力 | 剩余问题 |
| --- | --- | --- | --- | --- |
| 第一阶段：固定 Workflow | 选表、知识注入、SQL 生成、查询、图表与总结 | 先跑通完整问数链路 | 自动完成基本问数任务 | 缺少充分的多轮支持和执行反馈修复；SQL 与总结仍可能出错 |
| 第二阶段：整体封装为大 Tool | 将原流程作为工具接入 Agent Loop | 低成本引入多轮和重新尝试能力 | 外层 Agent 可以调用问数流程 | 中间状态不充分可见；修复粒度粗；总结计算幻觉明显 |
| 第三阶段：Skill + Reference + Python | Skill 调用问数工具，并引导模型使用参考资料和脚本分析结果 | 将数值计算从语言生成交给可执行代码 | 分析过程有步骤指导，数值有计算依据 | 问数工具内部仍较粗；调用脚本、数据流与重试不一定都被程序强制管理 |
| 第四阶段：细粒度 Agent 工具调用 | 进一步拆分上下文获取、SQL、执行、分析等能力 | 支持阶段性观察与局部修复 | 按工具结果决定下一步，而不必总是重跑整条流程 | 需要治理调用次数、状态、错误、权限与成本 |

四个阶段不意味着 Workflow、Tool、Skill 和 Agent 相互替代。它们可以同时存在：外层 Agent 决定下一步，Skill 提供操作方法，Tool 执行具体能力，确定性子流程仍然可以保留为 Workflow。

## 3. 第一阶段：先解决“模型拿什么信息生成 SQL”

### 3.1 业务元数据治理

项目首先需要明确服务的业务场景和高频问题，再整理 SQL 生成所需上下文：

- SQL 方言与查询引擎约束。
- 表的用途和粒度。
- 字段描述、类型、取值范围、枚举与单位。
- 时间字段与统计期间的定义。
- 常见指标的计算口径，例如记录数和去重客户数的区别。

面试表达：

> 我们发现，Text2SQL 的错误不只是 SQL 语法错误，更多时候是业务语义不明确。例如“客户数”应该用 COUNT 还是 COUNT DISTINCT，必须先定义口径，不能让模型每次自由判断。

这里可以称为业务语义治理，但不要直接等同于 Wren MDL 那样的可执行语义编译层，除非项目确实实现了类似机制。

### 3.2 两阶段选表

```text
用户问题
  → BERT 类小模型召回 Top 5 候选表
  → 轻量 LLM 二次筛选
  → 保留 1～3 张相关表
  → 加载相应 Schema
```

原因：表多、字段多，特别是存在上百字段的宽表时，直接提供全部内容会扩大上下文，增加字段选择和过滤条件错误。

面试重点是讲清取舍：二次选表能精简上下文，但多一次模型调用，也可能漏掉必要关联表。不要只说“越少越准确”。实际如何保留关联表、如何测试召回率，需要准备真实实现。

### 3.3 两类知识动态注入

| 检索入口 | 注入内容 | 目的 |
| --- | --- | --- |
| 表名 | 表级通用知识、字段使用限制、业务背景 | 说明选中的表如何正确使用 |
| 用户问题 | 专业术语、聚合指标、语义映射与 few-shot | 将具体问题映射成正确查询 |

问题级知识通过关键词与向量检索召回，然后动态加入 Prompt。

面试表达：

> 我们既检索 Schema，也检索“这些数据应该怎样使用”的业务知识，减少模型对口径和枚举的猜测。

## 4. 第二阶段：把 Workflow 包成大 Tool，为什么还会出问题？

### 4.1 先讲当时为什么选择这个方案

> 为了低成本利用已有流程，我们把完整问数 Workflow 封装成一个工具，让外层 Agent 调用。这样能够利用会话上下文，并在一次调用不满足需求时重新尝试。

这是一种合理的增量改造，不需要把早期方案描述成错误选择。

### 4.2 两类限制要分开说

**限制一：工具粒度太粗。**

```text
Agent 调用问数工具
  → 工具内部选表、生成 SQL、执行、分析
  → Agent 主要看到最终输出
```

中间状态没有充分进入外层循环，模型很难判断问题出在选表、SQL、执行还是分析阶段，经常只能改写问题并重跑。

**限制二：查询结果到分析结论之间仍可能失真。**

你补充的典型问题是：模型直接对查询结果进行数据分析和总结，可能出现计算错误、前后矛盾、无依据数字或无数据时强行解释。

面试时建议把“LLM 天生对数字不敏感”改成更准确的表述：

> 当时的分析环节主要依赖模型直接生成文字，没有通过确定性计算校验数值。对于增长率、占比和多步聚合等任务，生成结果可能不稳定；同时，模型还可能对没有证据的原因作出解释。

不同错误需要不同方法处理：

| 错误类别 | 例子 | 处理方向 |
| --- | --- | --- |
| 计算错误 | 增长率算错、总和与分项对不上 | Python / SQL 执行计算 |
| 口径错误 | 客户数未去重、分母选错 | 明确指标与粒度，校验参数 |
| 无依据数字 | 报告出现输入与计算结果中不存在的数值 | 数值来源绑定与结果校验 |
| 无依据解释 | 仅凭增长就断言由某次活动导致 | 限定证据范围，区分事实与假设 |

Python 能帮助解决计算问题，但不能自动修正错误口径，也不能自动证明因果关系。

## 5. Prompt 优化：如何介绍成一套方法论

你已说明做过系统提示词优化，但尚未提供实际 Prompt 版本。以下是一套建议用于复盘的框架：只将真实实施过的内容写入自己的经历，其余作为后续改进方向。

### 5.1 从失败案例出发，不只写“请保证准确”

建议按五步复盘：

1. **收集失败案例**：保存用户问题、查询结果、原回答，明确哪一句或哪个数字错误。
2. **按错误类型归因**：区分计算、口径、编造、空结果处理和结论冲突。
3. **把抽象要求改成可观察动作**：例如不只是“不要幻觉”，而是“没有同比基期时不得计算同比”。
4. **增加输入输出约定和边界示例**：明确列名、单位、日期、空值及零分母如何处理。
5. **在固定问题集上回归**：记录每版 Prompt 的正确率、遗漏率、成本和延迟，避免只修好单个案例。

### 5.2 可以组织为四层提示约束

| 层次 | 说明 | 示例 |
| --- | --- | --- |
| 证据边界 | 哪些信息可以用于回答 | 只能依据当前查询结果、计算输出和已提供业务规则 |
| 计算协议 | 指标如何定义与计算 | 环比为 `(本期−上期)/上期`，基期为零时返回不可计算 |
| 输出结构 | 事实、数字、解释如何呈现 | 先列核心指标，再描述现象，最后说明限制 |
| 异常与未知处理 | 缺数据时如何退让 | 空结果只说明当前条件下无匹配数据，不编造业务原因 |

### 5.3 一个可用于解释思路的 Prompt 示例

以下是建议模板，不是对当时实际系统提示词的还原：

```text
你负责基于查询结果生成业务分析。

数据依据：
- 仅使用输入数据、已知业务规则和工具计算结果。
- 缺少的数据明确说明，不补造数值。

计算要求：
- 金额、占比、增长率等衍生指标必须依据明确公式。
- 单位、统计期间、分母和去重口径必须一致。
- 若提供计算工具，衍生指标通过工具计算，不凭语言生成数值。

异常处理：
- 空结果、缺失基期、零分母分别说明。
- 结果被截断时，不把局部样本合计描述成全量合计。

输出要求：
- 区分数据事实、计算结果和待验证解释。
- 不从相关变化直接推导因果结论。
- 每个关键数字应能对应输入字段或工具输出。
```

### 5.4 为什么 Prompt 仍然不够？

> 提示词能够引导模型遵循计算和表达规范，但它本身不会执行算术，也不会阻止不符合要求的答案被输出。如果没有外部计算和程序校验，模型仍可能在复杂数字任务中出错。

因此，Prompt 优化的收益是降低错误概率，不能作为计算正确性的保障。

同样，让模型“再检查一遍”不能替代独立计算核验；模型可能重复同一个错误。

## 6. 第三阶段：用 Skill 组织流程，用 Python 承担计算

### 6.1 你补充的方案

```text
用户分析需求
  → 加载分析 Skill
  → 调用问数工具取得数据
  → 读取 Reference 中的分析规范和口径说明
  → 调用 Python 脚本计算分析指标
  → 根据计算结果组织图表与文字
```

可以这样讲：

> 发现单靠 Prompt 无法稳定解决计算错误后，我们把分析流程整理为 Skill。Skill 中组织问数工具调用、分析参考资料和 Python 脚本，让模型负责选择分析任务与解释结果，把具体数值计算交给代码执行。

### 6.2 Skill、Reference、Python 各自负责什么？

| 组成 | 责任 | 边界 |
| --- | --- | --- |
| Skill | 指导何时查询、如何分析、何时输出 | 文本步骤本身不是强制执行的程序 |
| Reference | 提供指标定义、边界处理、报告规范等资料 | 错误或过期的口径仍会导致错误结果 |
| Python 脚本 | 对实际数据执行聚合、计算或校验 | 输入、公式和脚本必须正确 |
| LLM | 理解需求、选择步骤、解释工具结果 | 仍可能误选指标或作无证据解释 |

特别注意：Skill 不是计算引擎。可靠性改善主要来自外部代码执行和相应的数据约束，而不是“换成 Skill”这个名称。

### 6.3 用一个例子解释改造价值

以下为教学案例，不是项目实测记录：

查询返回本月销售额 120 万元，上月 100 万元。

直接总结时，模型需要自行完成：

```text
差额 = 120 − 100 = 20 万元
环比 = (120 − 100) / 100 = 20%
```

改造后，Python 计算并返回结构化结果：

```json
{
  "metric": "sales",
  "unit": "万元",
  "current": 120,
  "previous": 100,
  "absolute_change": 20,
  "growth_rate": 0.2,
  "growth_rate_status": "valid"
}
```

模型基于这些数值生成：

> 本月销售额为 120 万元，较上月增加 20 万元，环比增长 20%。

但模型不能仅凭这些数值进一步断言“增长由促销活动导致”，除非另有证据。

这个例子也暴露了必须约定的边界：`0.2` 是比例，应展示为 `20%`；若上月为零，应返回明确状态，而不是随意填一个增长率。

### 6.4 如何陈述效果

你描述这一改造大幅降低了计算幻觉。正式面试时建议分清观察与量化证据：

- 有问题集和统计：说明测试范围、错误率变化和具体样例。
- 只有观察与案例：说“在已复盘案例中减少了这类计算错误”，并展示前后输出。
- 不要写“彻底消除幻觉”，因为公式选择、数据口径、脚本使用和解释仍可能出错。

## 7. 为什么引入 Skill 后，还需要细粒度工具调用？

### 7.1 问题不在于 Skill 天然粗，而在于剩余的执行边界

准确的表述是：

> Skill 改善了分析方法和计算过程，但当时问数能力仍以较大的工具暴露，内部选表、SQL 生成和执行过程没有充分拆开。Skill 提供的是操作指导，部分阶段的输入输出、失败处理和重试边界还没有被明确建模，所以局部修复仍不够直接。

不要说“Skill 必然比 Tool 粗”。Skill 可以指导细粒度工具调用，两者是互补关系。

### 7.2 后续改造的目标

不是把所有函数都做成工具，而是围绕可独立观察、验证和修复的步骤划分边界。

可参考的工具拆分如下，名称与参数为设计示例，请替换成实际实现：

| 能力 | 输入 | 输出 | 局部失败时的处理 |
| --- | --- | --- | --- |
| 记忆召回 | 问题、项目范围 | 相关问句-SQL 示例 | 无命中时继续检索上下文 |
| 获取业务上下文 | 问题、候选表 | Schema、口径、枚举、关系 | 重新选表或补充资料 |
| SQL 生成或修正 | 上下文、约束、错误反馈 | 候选 SQL | 保留已有上下文重新生成 |
| SQL 执行 | SQL、执行限制 | 数据或结果引用、结构化错误 | 区分语法、权限、连接、超时 |
| 数据分析 | 结果引用、指标与参数 | 计算结果、图表或分析产物 | 修改分析参数，不重跑无关查询 |
| 保存示例 | 问句、SQL、质量状态 | 持久化结果 | 失败不必阻断当前回答 |

SQL 生成也可以是 Agent 自身的一步推理，不必单独做工具。是否封装，取决于模型分工、可测试性和实际编排需求。

### 7.3 细粒度的价值在局部修复

```text
选表错误 → 重新获取上下文
字段错误 → 查看字段信息并修正 SQL
连接错误 → 返回环境问题，不反复让模型改 SQL
分析参数错误 → 重算分析，不重新查询所有数据
信息不足 → 澄清，而不是不断猜测
```

这些路径需要程序或编排策略落实。仅仅提供更多工具，不会自动获得可靠的自我纠错。

## 8. 三分钟项目介绍稿

> 我做的是一个自然语言问数与分析平台，用户提出业务问题后，系统会完成相关数据表检索、SQL 生成执行，再输出图表和分析结论。我主要负责【实际职责】。
>
> 第一版采用固定 Workflow。为了提高 SQL 生成质量，我们先治理字段描述、枚举、单位和业务口径，再做两阶段选表：通过 BERT 类小模型召回 Top 5 表，再由轻量模型筛选 1～3 张相关表。同时按表名召回通用业务知识，按用户问题通过关键词和向量检索召回相关口径及 few-shot，动态构造生成上下文。
>
> 跑通链路后，我们希望利用多轮上下文和执行反馈，因此先将整条 Workflow 封装成一个工具，接入 Agent Loop。这种方式改造成本低，但工具粒度比较粗，外层模型对中间过程的可见性不足，失败时经常只能重新执行整个流程。
>
> 其中一类典型问题出现在数据分析总结阶段。模型直接根据查询结果生成文字时，会出现计算错误、前后矛盾，以及无数据依据的解释。我们先通过系统提示词约束数据来源、指标口径、异常处理和输出方式；【这里替换为实际做过的 Prompt 优化动作】。但 Prompt 本身不执行计算，也不能强制保证数值正确。
>
> 因此我们进一步把分析流程整理成 Skill，在其中调用问数工具，并提供参考资料和 Python 脚本。模型负责理解任务和解释结果，具体指标交给代码计算。这降低了直接依赖语言生成进行数字计算的风险，实际效果可以通过【真实案例或评测结果】说明。
>
> 不过，Skill 改善的是流程指导和分析方法，当时底层问数工具仍然比较粗，所以后续继续细化 Agent 的工具边界，让上下文获取、SQL 执行和分析都有更明确的反馈，以便局部修复。同时继续治理字段和常用聚合中间层，降低复杂查询的生成难度。
>
> 这个项目的核心体会是：Prompt 用来指导模型，代码负责确定性计算，工具反馈支持 Agent 决策；可靠性来自这些环节配合，而不是单独换一个模型或框架。

如果最终细粒度方案仍在试验，应把“实现了”改为“正在尝试”，并明确已经完成的部分。

## 9. 面试需要重点准备的六个主题

### 主题一：一个真实的计算幻觉案例

准备材料：用户问题、原查询结果、原回答、错误位置、Prompt 调整后的结果、Python 改造后的结果。

重点回答：

- 是加减乘除错了，还是公式、分母、单位、粒度错了？
- 你怎么证明错误发生在总结阶段，而不是 SQL 阶段？
- 计算改正确以后，文字是否仍可能捏造原因？

这是最能支撑架构演进动机的证据。

### 主题二：Prompt 优化的真实过程

准备至少一组优化前后的 Prompt 差异，不只展示最终版本。

重点回答：

- 新增约束针对哪类失败？
- 是否增加了空数据、零分母、缺失基期示例？
- 是否出现过模型变得过于保守、拒绝回答更多问题？
- 用什么问题集验证改善，是否只在单个案例有效？

可以用“失败案例 → 归因 → 明确约束 → 示例 → 回归”的顺序讲述。

### 主题三：Skill、Tool 与 Agent Loop 的职责

建议用三个具体对象解释：

- Tool：可以被执行的能力及输入输出契约。
- Skill：完成某类任务的方法、参考资料与可用脚本。
- Agent Loop：根据当前状态和工具结果决定下一步的循环。

重点回答：

- Skill 如何加载？什么时候读取 Reference？
- Python 脚本由谁触发，是否允许跳过？
- 哪些错误会回到模型上下文？
- 为什么你后续还需要更细的工具？

不要依赖某个框架名来替代机制解释。

### 主题四：Python 分析的数据与执行契约

图片和补充中没有这些实现细节，需要按真实项目补齐：

- 查询结果通过 JSON、CSV、DataFrame 还是文件引用传给脚本？
- 数据量大或被截断时怎样处理？
- 脚本是预置参数化脚本，还是模型动态生成？二者风险不同。
- 单位、空值、零分母、去重、精度怎样约定？
- Python 输出如何绑定到最终回答，避免模型再次改写数值？
- 如何控制执行超时、文件访问和资源占用？

建议准备一份真实输入与输出示例。能解释清楚数据流，比泛泛说“接了 Python 工具”更有说服力。

### 主题五：Agent 的修复与停止条件

重点回答：

- 如何识别选表、SQL、连接和分析错误？
- 哪些步骤可以复用结果，哪些必须重跑？
- 最大调用次数、超时、token 预算如何设置？
- 连续失败或业务信息不足时怎样停止并向用户反馈？
- 多轮问题改变了时间或指标时，旧结果如何失效？

不要将“有循环”直接当作“会自我纠错”。必须能说明一次失败后究竟改变了什么。

### 主题六：效果、成本与个人贡献

建议准备以下指标，按实际拥有的数据选择：

| 指标 | 回答的问题 |
| --- | --- |
| 相关表召回率 | 两阶段选表是否遗漏必要表？ |
| 查询结果正确率 | SQL 能执行之外，是否满足业务问题？ |
| 数值计算正确率 | Python 分析是否减少计算错误？ |
| 关键数值可追溯率 | 报告数字是否能找到数据或计算来源？ |
| 无依据结论比例 | 是否仍存在编造的解释？ |
| 修复成功率 | 在初次失败任务中，多少经过反馈得到正确结果？ |
| 延迟、调用数与 token 成本 | 可靠性提升付出了什么代价？ |

理想对照组是：直接总结、Prompt 优化、Skill + Python、细粒度 Agent。测试问题、数据快照和模型配置应尽量保持一致。

这些是建议的评测方式，不是项目已完成的实验。没有数字时，可以展示少量真实前后案例，但不能编造准确率。

最后明确自己的贡献：定义了哪些接口、写了哪些脚本、维护哪些知识、设计哪些修复分支、做了什么评测。

## 10. 容易被追问的表达，如何说得准确

| 容易说得过满的表述 | 更准确的表述 |
| --- | --- |
| LLM 天生不会算数 | 当时直接生成数值的方式缺少确定性校验，复杂计算可能不稳定 |
| Prompt 没用 | Prompt 能降低错误概率，但不能替代计算执行和结果校验 |
| 封装成 Skill 就没有幻觉了 | Skill 组织分析方法，Python 承担计算，仍需校验口径和解释 |
| Workflow 无法纠错 | 当时版本缺少细粒度反馈和修复分支；Workflow 也可以设计重试 |
| Skill 天然粒度粗 | 当时 Skill 依赖的问数工具仍较粗，部分阶段缺少明确执行边界 |
| Tool 越细越好 | 按可独立观察、验证和修复的边界拆分，避免增加无意义调用 |
| SQL 执行成功就保存为正确案例 | 需要明确质量标准，执行成功不保证业务正确 |
| Python 能保证分析正确 | Python 确定性执行给定逻辑，输入和公式错误仍会产生错误结论 |

## 11. 面试前的最小准备清单

- 一张四阶段演进图，能在一分钟内解释改造动机。
- 一个真实的总结计算错误案例，保留输入、输出和修复证据。
- 一组真实的 Prompt 优化前后差异。
- 一个 Skill 目录示例，说明指令、Reference 和脚本分别做什么。
- 一次完整工具调用轨迹，能解释局部失败如何处理。
- 一份真实结果或案例对照，以及清楚的个人职责边界。

讲述时把精力集中在“观察到的问题、做出的选择、验证结果和剩余限制”。这比堆砌 Agent、RAG、Skill、ReAct 等术语更能体现工程能力。
